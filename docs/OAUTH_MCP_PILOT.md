# Hosted workspace MCP authorization: pilot status

The current workspace connector is local stdio. `oauth_identity.py` and `hosted_workspace.py` provide a tested, stateless MCP-over-HTTP resource server with token validation, protected-resource discovery, and workspace-scoped setup tools. `oauth_consent.py` implements the consent decision, `supabase_oauth_provider.py` authenticates and fetches provider-verified authorization details, and `sqlite_oauth_grants.py` persists local grants and revocations. `consent_routes.py` provides a tested browser API with session-bound encrypted review state and CSRF checks; `supabase_oauth_grants.py` provides a PostgREST adapter for the grant table. The generated grant migration was replayed on disposable PostgreSQL with access-control checks. On 2026-11-14 its SQL was also applied to the geosition-pilot production database through the Supabase SQL editor. A production catalog query verified RLS, denial of SELECT to anon and authenticated, service-role access, and the membership foreign key and permission constraint. The dashboard schema application did not register migration history; the verified baseline was subsequently recorded as described below. `hosted_bootstrap.py` installs both components only when explicitly activated with persistent Supabase storage and valid configuration. The production feature flag `GEOSITION_HOSTED_MCP_ENABLED` is off by default and has not been enabled or deployed. The tested SDK version is MCP 1.27, which must be included in the deployment dependencies before activation.

The platform has its own password/session users in `geo_platform_users`, while Supabase Auth issues separate user identities. Do not match accounts by email. An account-linking flow must authenticate both identities and obtain explicit workspace and client consent before persisting a grant. Each grant needs a trusted issuer, immutable provider subject, OAuth client ID, GEOSITION user ID, workspace ID, permissions and revocation state. Every tool call must verify the issuer, resource audience, token signature and expiration; resolve the exact active grant; and recheck current workspace membership and permissions. Revoked grants and removed memberships must stop access.

Supabase's default OAuth access-token audience is `authenticated`, not this MCP resource. Configure and verify an appropriate resource-specific audience before accepting any token. OIDC scopes such as `openid` and `email` do not grant platform or database permissions. Do not assume database RLS protects GEOSITION's current service-role-backed store.

As of 2026-11-14, [Supabase Auth issue #2610](https://github.com/supabase/auth/issues/2610) is open and reports that the OAuth server accepts `resource` without binding it into the access-token audience. The pilot's OAuth discovery endpoint was disabled when checked, so this has not been verified against the pilot version. Do not enable dynamic registration or issue an MCP audience to every OAuth client as a blanket workaround: the actual requested resource must be securely bound through authorization, token exchange, and refresh. Validate a supported issuer or a narrowly designed, independently reviewed alternative with real client flows before enabling the feature.

The owner consent page and its session-bound API are implemented and tested locally, but the router is not mounted. The page currently requires an existing Supabase AI identity account, which must be provisioned through a separate flow; self-service registration and account recovery are not implemented.

Remaining integration: verify CLI migration listing and hosted branching compatibility; configure issuer JWKS and resource-specific token audience; include the MCP SDK in production and deploy with the endpoint disabled; validate configuration and activate the hosted MCP Streamable HTTP server; then test PKCE, registration, consent, refresh, revocation and cross-workspace denial with ChatGPT and Claude. Supabase OAuth server and dynamic registration require deliberate configuration; do not enable public registration without a working consent flow and safeguards. Supabase may auto-approve previously granted requests before returning authorization details; the consent logic fails closed in that case rather than inferring a client or workspace.

The included HTTP and authorization tests use locally signed tokens and simulated pilot identities. They do not establish live OAuth interoperability or access to the actual business workspaces.

## Auth0 pilot investigation (2026-11-14)

A US-region Auth0 development tenant was created after owner approval. Its resource-parameter compatibility profile is enabled, and the custom API `https://www.geositionai.com/mcp` uses RS256, per-application delegated authorization, and no machine-to-machine client access. These settings are preparatory: no ChatGPT or Claude application has been authorized and the hosted GEOSITION endpoint is not connected to Auth0. The dashboard reports a 22-day trial; verify the features and pricing after the trial before relying on this setup.

The existing account-linking and consent adapter is specifically implemented against Supabase Auth. Switching issuers requires a separately designed and tested Auth0 integration that verifies the issuer, subject, client, resource, workspace membership, and the owner's informed consent. Do not point the existing Supabase adapter at Auth0 or enable the connector based only on the API configuration.

A fresh production catalog check found the grant index and invitation function, and no public `geo_` tables without RLS. At that point the CLI history table did not exist; the subsequent schema comparison and history repair are recorded below.

In a temporary environment, the hosted integration, activation, workspace, local OAuth, bootstrap, identity, consent, Supabase grant, and Supabase provider test files passed: 11 tests total. These use simulated identities and do not establish live ChatGPT or Claude connectivity.

## Baseline comparison and Auth0 token profile

On 2026-11-14 the seven local migration files were replayed successfully into an isolated PostgreSQL 16 instance. Schema catalog fingerprints matched the live pilot for all 18 `geo_` tables and row-security flags, 146 columns, 44 constraints, and 34 indexes. The invitation function matched after whitespace normalization. Live checks also confirmed anon/authenticated cannot execute that function or read the grant table, while service_role retains the required privileges. These comparisons do not establish application integration or migration history; the history table was not modified during that comparison. It was subsequently repaired as described below. The temporary PostgreSQL server was stopped.

The GEOSITION Auth0 API was changed to the RFC 9068 token profile and skipping user consent was disabled. Auth0 documents that this profile provides the `client_id` claim expected by the existing verifier. No actual Auth0 access token has yet been issued or tested; the existing Supabase-specific linking and consent code remains unadapted.

## Migration-history baseline recorded

On 2026-11-14 a transaction through the Supabase SQL editor checked the previously compared table, column, constraint, index and invitation-function fingerprints and required the history table to be absent. It then created `supabase_migrations.schema_migrations` and recorded versions 002–007 and 20261114085138 with names and NULL statement arrays. Supabase's editor enabled row level security; anon and authenticated lack schema usage. The seven version rows and these permissions were queried after the transaction. The same transaction passed on a temporary replay database and refused a second execution. This was a dashboard SQL repair, not the CLI `migration repair` command; `supabase migration list` and hosted branching compatibility have not been tested. NULL statement arrays do not preserve historical SQL in the ledger; the migration files remain the source of those statements.

The Auth0 consent routes, owner-only workspace approval, signed continuation, page, opt-in bootstrap, and Post-Login Action source have local tests. They have not been deployed or connected to live Auth0 clients. The endpoint remains disabled until credentials, client allowlist, action, and live end-to-end verification are complete.

## Live setup progress

The pilot signing secret was stored as an Auth0 Action secret and Vercel production secret; it is not recorded here. The Auth0 Action remains an unbound draft. Auth0 has manually registered the published ChatGPT and Claude client metadata. The tenant-wide CIMD discovery setting remains disabled after automatic approval review rejected enabling it. As a narrower alternative, two fixed third-party OAuth clients were registered with the exact ChatGPT and Claude callbacks and per-client delegated access to the GEOSITION API; no machine-to-machine API access was enabled. Vercel production configuration includes the Auth0 issuer and fixed-client allowlist, but the hosted MCP enable flag remains off.

Supabase MCP listed all seven recorded migrations. Security advisors reported informational RLS-without-policy notices for the 18 public GEOSITION tables; the server-side service-role access model intentionally does not provide public client policies. Production release `geosition-eo68l85p5-arnaud15.vercel.app` was deployed with MCP disabled; `https://www.geositionai.com/health` returned status ok, and the Auth0 consent route returned 404 as expected while disabled.

Auth0 states that strict third-party applications cannot use the existing username-password connection until it is promoted to domain level, which makes it available to all third-party applications in the tenant. Owner approval was requested for that change. Neither AI client has been connected to the live connector and no real pilot OAuth flows have been tested. Auth0 tenant currently has no users. Hosted branching and CLI migration-list checks remain outstanding.
